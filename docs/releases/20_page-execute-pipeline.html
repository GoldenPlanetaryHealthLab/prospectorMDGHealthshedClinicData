29  Execute the Pipeline

Keep rendering and scientific execution separate

The historical branch uses the hand-delivered May 2025 ZIP exclusively and dynamically branches the approved W3 CSV preparation and legacy clinic-month inventory work. Page 16 tracks that ZIP and extracts only its selected W3 and reviewed mapping sources; the Google Drive/rclone mirror is excluded from historical inputs and comparisons. Branching is declared here rather than in the transformation notebooks: each notebook defines one-file transformation logic, while this graph defines dependencies and the scheduler can distribute independent branches. Clinic-month branches track one Parquet file per monthly member of the staged ZIP. Page 20 combines their paths into a single Parquet inventory before collecting the reduced identity table. Page 21 constructs the cross-wave diagnosis dictionary from the prepared Wave 3 schema and archived source dictionaries and translations. Page 22 cleans and maps diagnosis measurements, selects report sources, and branches over dictionary output groups. S4 currently uses the existing serial runner; Slurm and controller configuration are outside this implementation. Page 23 reconciles the frozen sectorization and reviewed spatial corrections, constructs clinic healthsheds, and retains ordinary sf handoffs for pages 24–25. A cheap always-check target records the spatial package/native engine versions and s2 setting; changed values invalidate the spatial read. Page 24 assembles frozen coordinate sources, tests row-aligned intersections, and retains candidates and the selected source for page 25. Page 25 combines reporting history, reviewed spatial attributes, coordinate selection, and neighbor evidence into two tracked metadata Parquet products.

Pages 26–28 implement the separate 2025–2026 source survey, cleaning, and geospatial/final-aggregation work. Those deliveries are outside the old-wave ZIP. These pages are now included by tar_tangle() here. The graph includes both approved deliveries, final-product validation, internal candidate packaging, and independent resource verification. Declaring or rendering this graph does not execute it. Stagecoach owns the inputs; tracked R values in the notebooks own transformation and release parameters. No separate preparation step is needed.

NoteTrack Data At Each Target Boundary

The current graph executes each per-file maximum in DuckDB and writes the result to a branch-specific Parquet file. targets stores those file paths rather than attempting to serialize live duckplyr relations. Page 18 declares the final cross-file aggregation and cleaned Parquet output, included through tar_tangle(). In-memory tables remain ordinary data targets; source files and derived Parquet paths use format = "file" so their contents are tracked.

For dynamic file inputs, keep the path selector separate from file tracking. s0_clinic_RMA_W3_raw_paths_chr returns the selected path vector as an ordinary target. s0_clinic_RMA_W3_raw_csv then tracks one file per branch, and the Parquet reducer branches over those tracked files. A static file target would treat the whole vector as one bundle and cannot serve as that branch dimension. This is the documented file-branching pattern.

Important Prerequisite: Confirm The Execution Boundary

The runtime image and frozen R package library must exist. Approved inputs must be staged under data/inputs. Run scientific target builds only inside the compute-node allocation. Rendering and static/synthetic checks do not build targets.

29.1 Parallel targets execution plan

Tip Procedure: Plan One Allocation With Local Target Workers

Planned configuration, not enabled by this page yet. Legacy stage 4B is absorbed into the existing runner and targets execution boundary. Submit one Slurm allocation through the page-15 launcher and run one tar_make() manager inside the project container. The manager will dispatch ready targets to local R worker processes within that allocation.

The planned backend is the supported crew local controller, selected through tar_option_set(controller = ...). The ordinary tar_make() call remains the execution entry point; it has no new worker-count argument. Do not port stage 4A’s future::plan(multicore), future_map() pools, or future.globals.maxSize overrides into individual targets. Do not submit one Slurm job for each diagnosis partition or use a Slurm worker-launcher plugin for this single-allocation plan.

Illustrative configuration for a future reviewed resource profile:

# Planning example only: not part of the emitted _targets.R below.
# Declare and lock crew through page 14 before enabling this configuration.
tar_option_set(
  controller = crew::crew_controller_local(workers = 2L)
)

Two workers are an example, not an established memory-safe default. Select the worker count from measured branch requirements and the approved allocation. The local controller creates separate R processes on the manager’s node; additional allocated nodes do not automatically become workers.

Tip Procedure: Plan Branch Memory, Threads, And Scheduling

Keep measurement-heavy operations inside bounded stage-4 targets and pass Parquet paths between them. Schedule independent monthly, complete-period, and output-group branches in parallel. Keep ordered spatial correction rounds and other dependent transformations in their scientific sequence.

Before activation, record a versioned resource profile with:

Resource Required decision and verification
Allocation One manager task, approved CPUs, total memory, wall time, and shared writable project/scratch storage
Worker concurrency Explicit count within CPU and measured memory budgets, including manager overhead and retry behavior
Engine threads Explicit per-worker DuckDB/BLAS thread budgets; do not give every worker the whole allocation’s CPU count
Memory Branch peak R plus engine memory, manager memory, and headroom; engine settings alone are not evidence of total process memory
Files Branch-unique outputs, private temporary extraction/scratch, and read-only shared inputs
Environment Same container, project working directory, and locked R library in every worker; initialize connections inside each process

Use a representative month and output group as the first pilot. If a branch does not fit its budget, reduce its working set or partition it at a safe scientific boundary before increasing concurrency. Parallel execution does not divide the memory required by one oversized target. Do not request a blanket high-memory stage-4 job to compensate for collecting all waves in R.

Add crew to the direct dependency declaration and lock it only when the controller implementation is introduced. The current _targets.R, runner, and dependency lock remain unchanged by this detailed plan. The target graph shown below is the currently implemented graph; pages 18–30 and internal candidate packaging are now wired into it.

Tip Procedure: Emit The Pipeline Entry Point 
#!/usr/bin/env Rscript

script_arg <- grep("^--file=", commandArgs(trailingOnly = FALSE), value = TRUE)
script_path <- if (length(script_arg)) sub("^--file=", "", script_arg[[1]]) else ""
if (!nzchar(script_path)) {
  stop("Could not determine the pipeline runner path.")
}

repository_root <- normalizePath(
  file.path(dirname(script_path), ".."),
  mustWork = TRUE
)
setwd(repository_root)
targets::tar_make()
