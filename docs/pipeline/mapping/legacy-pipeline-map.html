8.2 Workflow data storage convention

Across our workflows, keep all data in targets objects or in Parquet files tracked as file targets. In-memory tables, lists, and spatial sf objects remain ordinary targets. When a transformation persists data outside the target store, it writes Parquet and returns the path from a target declared with format = "file". A path stored in an ordinary character target does not itself track the file’s contents. A _parquet suffix documents the format; it does not replace the file-target declaration.

Branch-driver path vectors are ordinary targets containing selection metadata. When processing files individually, map that vector into a format = "file" target with its own pattern, then map the transformation over those file branches. A static file target treats its returned paths as one indivisible bundle, so it cannot be used as the dimension for per-file branching.

Staged source files retain their original CSV, Excel, ZIP, or spatial formats and provenance, and are also tracked as file targets. Temporary extraction and scratch files can exist within a target’s execution; downstream stages consume the returned object or tracked Parquet artifact. Diagnostic notebook queries use tar_read() or tar_load() and do not create separate persistent data copies. Ordinary targets may use RDS internally in the target store; the convention concerns how workflow data is handed between stages.

In tangled notebooks, #| format: file applies to every assignment in that code chunk. Keep path declarations in separate chunks from in-memory data transformations so tables are not accidentally declared as file paths.

8.3.7 Reproduce the archive inspection

This read-only command inventories members without extracting the repository or running R. It prints active and commented writer sites separately for review, expands the diagnosis families, lists embedded reference members, and recomputes the selected byte hashes. The top-level inventory has 960 regular files after excluding .DS_Store and entries outside the repository root (including AppleDouble __MACOSX/ entries); this count includes .git/. Its SHA-256 fingerprint over sorted relative_path<TAB>size<TAB>CRC32 records joined by newlines, with no trailing newline, is f00e476d2e904a29684e97f4fbe1aab7cd85492221b126cc10c8eef713c6ea84. This fingerprints the directory metadata, not the entire ZIP byte stream.

from pathlib import Path, PurePosixPath
from io import BytesIO
import hashlib
import re
import zipfile

archive = Path("data/inputs/01_gold_mine/gdn_datafreeze_may2025/"
               "madagascar_clinic_data_cleaning.zip")
root = "madagascar_clinic_data_cleaning/"
with zipfile.ZipFile(archive) as z:
    members = {
        i.filename.removeprefix(root): i for i in z.infolist()
        if i.filename.startswith(root) and not i.is_dir()
        and PurePosixPath(i.filename).name != ".DS_Store"
    }
    records = "\n".join(
        f"{name}\t{i.file_size}\t{i.CRC:08x}"
        for name, i in sorted(members.items())
    )
    print("Archive bytes:", archive.stat().st_size)
    print("Inventory files / SHA-256:", len(members),
          hashlib.sha256(records.encode()).hexdigest())
    writers = re.compile(r"write\.csv|write_feather|saveRDS|st_write|"
                         r"tmap_save|ggexport|ggsave|R CMD BATCH")
    for name, i in sorted(members.items()):
        if name.startswith("scripts/") and name.endswith((".R", ".slurm")):
            content = z.read(i)
            print("SCRIPT", name, "SHA-256", hashlib.sha256(content).hexdigest())
            for n, line in enumerate(content.decode("utf-8-sig").splitlines(), 1):
                if writers.search(line):
                    state = "commented" if line.lstrip().startswith("#") else "active"
                    print(n, state, line.strip())
    for name, i in sorted(members.items()):
        if name.startswith(("data/clean/", "data/intermediate/", "scratch/")) or (
            "wave3_with_keys" in name or "/oreillon_" in name
        ):
            print("MEMBER", name, i.file_size, f"{i.CRC:08x}")
    with zipfile.ZipFile(BytesIO(z.read(root + "data/intermediate_ref_tables.zip"))) as nested:

8.6 How the responsibilities connect

Three different kinds of mapping are involved. The facility mapping links a year-specific GESIS code to a DHIS2 facility UID. The clinic identity crosswalk follows a clinic through code and name changes. The diagnosis dictionary defines comparable measurement variables across reporting systems. The first two identify who reported; the third defines what was reported.

The spatial branch assigns administrative areas called fokontany (FKT) to clinics and unions their polygons into healthsheds. These are based on the 2022 sectorization. Their use alongside earlier reporting data does not itself establish historical catchment boundaries.

8.18 Assignment-to-target inventory

This inventory maps the legacy assignments to named responsibilities in the replacement graph. It is a design index; no targets are created or rewired by these tables.

Identifiers use script::variable, for example 1::mapping. The script keys match the filenames in the crosswalk; 999 denotes the utilities and checks denotes data_checks.R. A repeated variable is qualified by its stage because an in-place reassignment can represent a different scientific operation. Function-local values are listed with their owning operation, and short setup/read/normalization steps may share one target. Columns created inside mutate(), summarise(), or := belong to the assigned table; the important column stages are named in the rows rather than proposed as individual targets. Commented-out alternatives are not active assignments; the commented inventory builder in script 2 is retained as provenance for its active inventory read.

Existing means the exact name is declared in the current pipeline notebooks or _targets.R; it does not establish that the target has completed. A row can map to an existing target that already groups several legacy operations. Where the new pipeline changes storage or avoids a large intermediate, the mapping identifies the owning transformation, not an identical R object. Recommended names describe results or responsibilities still to be introduced or separated from a coarse target. Names shared across scripts identify the same producer/consumer handoff, not duplicate proposed targets. Recommended suffixes describe the intended R value or replacement Parquet format; implementation and branching remain to be decided.

Helper definitions are grouped with their owning data responsibilities in the legacy inventory below. In the current notebooks, tar_tangle() also turns top-level function assignments into targets; those use the _fn suffix. Diagnostic and exploratory objects are identified explicitly. Their inclusion preserves the question being asked; it does not promote every scratch expression to a validated scientific rule. The input inventories and current file selectors remain the common staging boundary. Rows for legacy final writes are included even when the write call has no assigned return value. Their replacement handoffs reuse ordinary data targets or name tracked Parquet artifacts.

8.18.1 Target naming convention

Use script-stage_domain_contextual-name_[modification-in-pipeline]_R-data-type, with underscores between words. The modification is optional. For example, s0_clinic_RMA_W3_group_max_parquet is the script 0 clinic/RMA Wave 3 group maximum artifact, and s1_gesis_xwalk_clean_df is the script 1 cleaned GESIS crosswalk in R.

The stage identifies the producing legacy script, not the notebook number or the consuming script: s0 through s7, with s4a for measurement cleaning. Exploratory checks use schecks. Shared utility operations keep the stage of their owning transformation. Common staging inputs use s0_pipeline.

Suffix Value represented
df In-memory data frame or tibble
